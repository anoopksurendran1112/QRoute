Export inferred types RegisterInput and LoginInput. The register schema deliberately has no role field — role assignment is server-side only, and a client-supplied role must be stripped by zod's default object behaviour rather than honoured. Append `export * from "./schemas/auth.ts"` to packages/shared/src/index.ts (the barrel was created in 01-03; this plan owns the addition).

Create apps/api/src/utils/jwt.ts using jsonwebtoken: signToken(payload: { id, role, email }) signs { sub: id, role, email } with config.jwtSecret, expiresIn "7d", issuer "qroute"; verifyToken(token) calls jwt.verify with `algorithms: ["HS256"]` (an explicit allowlist stops algorithm-confusion attacks) and issuer "qroute", returning a typed payload { sub, role, email } or throwing. Never accept the algorithm from the token header.

Create apps/api/src/utils/password.ts using bcryptjs only (never the native bcrypt package, which needs node-gyp and MSVC on Windows): hashPassword(plain) uses config.bcryptRounds and returns the hash; verifyPassword(plain, hash) returns boolean via bcrypt.compare; a small `toPublicUser(user)` mapper returns { id, email, name, role } so no route can accidentally serialise the hash.

  <files>apps/api/src/middleware/auth.ts, apps/api/src/middleware/requireRole.ts, apps/api/src/middleware/rateLimit.ts, apps/api/src/modules/auth/router.ts, apps/api/src/routes/admin.ts, apps/api/src/app.ts</files>
  <action>
Create middleware/auth.ts exporting requireAuth: read the Authorization header, require the "Bearer " scheme, call verifyToken, attach { id: payload.sub, email: payload.email, role: payload.role } to req.user, and return 401 with ApiErrorCode UNAUTHORIZED for a missing, malformed, expired or badly signed token. Distinguish nothing about why verification failed in the response — the distinction belongs in server logs only.

Create middleware/requireRole.ts exporting requireRole(role) as a factory that returns 403 FORBIDDEN when req.user is absent or its role does not match, and calls next() otherwise. requireRole must never be the only guard on a route: it assumes requireAuth ran first, so every route registers requireAuth then requireRole.

Create middleware/rateLimit.ts exporting authLimiter built with express-rate-limit: windowMs config.rateLimitAuthWindowMs, limit config.rateLimitAuthMax, standardHeaders "draft-8", legacyHeaders false, skipSuccessfulRequests true (only failed attempts count against the budget, so normal logins are never throttled), and a handler that responds 429 { error: { code: "RATE_LIMITED", message } }. This closes the brute-force threat T-01-11 that the previous draft deferred with no owning phase. Mount it on both POST /v1/auth/register and POST /v1/auth/login.

Create modules/auth/router.ts:
- POST /register: parse with registerSchema; on failure 400 VALIDATION_ERROR with zod issue paths. Look up by email and return 409 CONFLICT if it exists. Hash with hashPassword, create the user with role "user" unconditionally — never with a role taken from the body. Respond 201 { token, user: toPublicUser(user) }.
- POST /login: parse with loginSchema; find by email; if the user is absent or verifyPassword fails, return the identical 401 { error: { code: "UNAUTHORIZED", message: "Invalid email or password" } } in both cases (no account enumeration); otherwise 200 { token, user: toPublicUser(user) }.
- GET /me: requireAuth then return { user: req.user }.
All handlers are plain async functions; Express 5 forwards rejections, so no wrapper is needed.

Create routes/admin.ts with GET /ping behind requireAuth and requireRole("admin") returning { status: "ok", user: req.user }. This endpoint exists so the role gate has a probe that does not depend on the catalog routes arriving in the next wave, and so the admin panel has a cheap session check.

Edit app.ts (created in 01-02) to mount the auth router at /v1/auth, the admin router at /v1/admin, and to keep the health router and the 404/error handlers as the last registrations. Order: helmet, cors, json, pino-http, health, auth, admin, 404, error handler.
