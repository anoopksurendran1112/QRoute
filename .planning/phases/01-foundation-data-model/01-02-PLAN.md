Create prisma/schema.prisma. The generator block must be `provider = "prisma-client"` (not the deprecated prisma-client-js), with an explicit `output = "../src/generated/prisma"` and `importFileExtension = "ts"` — the last setting is what stops tsx throwing "Cannot find module './internal/class.js'". The datasource block carries only `provider = "mysql"`; the connection URL lives in the Prisma config file in v7 and must not appear here.

Define enums Role { user, admin }, NodeKind { junction, door, stair, lift, entrance }, EdgeKind { walk, stair, lift }. Fields inside enums are lowercase; model names are PascalCase with `@@map` to snake_case table names (users, departments, faculty, buildings, floors, classrooms, nodes, edges).

Models and their required opposite relation fields — every relation must declare both sides, or `prisma validate` fails:
- User: id String @id @default(cuid()), email String @unique, password String (bcrypt hash only), name String, role Role @default(user), createdAt, updatedAt.
- Department: id, name String @unique, code String @unique, faculty Faculty[], classrooms Classroom[], createdAt, updatedAt.
- Faculty: id, name, email String @unique (this is the natural key the idempotent seed upserts on), designation String?, departmentId String, department Department @relation(..., onDelete: Restrict), createdAt, updatedAt.
- Building: id, code String @unique, name, campus String?, floors Floor[], createdAt, updatedAt.
- Floor: id, buildingId, building Building @relation(..., onDelete: Cascade), level Int, name String?, imagePath String?, imageSha256 String?, widthPx Int?, heightPx Int?, metersPerPixel Decimal @db.Decimal(10,6) NOT NULL (PITFALLS.md is explicit: this column is non-nullable from the foundation phase, because a placeholder scale silently makes every distance fiction), classrooms Classroom[], nodes Node[], @@unique([buildingId, level]).
- Classroom: id, roomNumber String, name String?, floorId, floor Floor @relation(..., onDelete: Cascade), departmentId String?, department Department? @relation(..., onDelete: SetNull), entranceNodeId String?, entranceNode Node? @relation("ClassroomEntrance", fields: [entranceNodeId], references: [id], onDelete: SetNull), capacity Int?, createdAt, updatedAt, @@unique([floorId, roomNumber]). The entrance relation requires Node.classrooms Classroom[] @relation("ClassroomEntrance") — this is one of the opposite fields the research sketch omitted.
- Node: id, floorId, floor Floor @relation(..., onDelete: Cascade), code String (stable human key such as M1-J1, used by the seed's upsert), kind NodeKind, x Decimal @db.Decimal(10,3), y Decimal @db.Decimal(10,3), label String?, edgesFrom Edge[] @relation("EdgeFrom"), edgesTo Edge[] @relation("EdgeTo"), classrooms Classroom[] @relation("ClassroomEntrance"), createdAt, updatedAt, @@unique([floorId, code]).
- Edge: id, fromNodeId, fromNode Node @relation("EdgeFrom", fields: [fromNodeId], references: [id], onDelete: Cascade), toNodeId, toNode Node @relation("EdgeTo", fields: [toNodeId], references: [id], onDelete: Cascade), kind EdgeKind @default(walk), costM Decimal @db.Decimal(8,2) NOT NULL (the only field the router will read — never derived from pixels at read time), accessible Boolean @default(true), bidirectional Boolean @default(true), createdAt, updatedAt, @@unique([fromNodeId, toNodeId, kind]). Two named self-relations on Node are mandatory: a single unnamed self-relation on Edge validates but produces an ambiguous client, so keep the EdgeFrom/EdgeTo names on both sides.

Because Prisma's CLI looks for prisma.config.ts by default and this file is deliberately named prisma7.config.ts to match the researched convention, every npm script passes --config prisma7.config.ts (already wired in plan 01-01). Do not rename the file and do not rely on the default lookup.

  <name>End-to-end health slice: HTTP request to DB round-trip and back</name>
  <files>apps/api/src/app.ts, apps/api/src/index.ts, apps/api/src/routes/health.ts, apps/api/scripts/smoke-health.ts</files>

Wire the thinnest complete path the phase will build on: an HTTP request through Express middleware, into the Prisma client, out to MySQL, and back as JSON.

src/routes/health.ts exports a Router with GET / returning 200 { status: "ok", db: "ok", uptimeSeconds } after awaiting `prisma.$queryRaw` with SELECT 1; if the query throws, respond 503 { status: "degraded", db: "unreachable", error: <message> }. This is the only place in the phase that proves the database is actually reachable.

src/app.ts exports `createApp()` returning an Express 5 app with, in this order: helmet(), cors({ origin: config.corsOrigin, credentials: false }), express.json({ limit: "1mb" }), pino-http with config.logLevel, the health router mounted at /v1/health, a JSON 404 handler for unknown /v1 paths, and a final four-argument error handler that maps thrown errors to { error: { code, message } } without leaking stack traces. Because Express 5 forwards rejected promises from async handlers automatically, do not add express-async-handler. Note request order matters: cors and json must be registered before routes, and the error handler last.

src/index.ts loads config first (so a bad environment fails before the port opens), calls createApp().listen(config.port), logs the bound URL, and installs SIGINT/SIGTERM handlers that close the server then call disconnectPrisma() before exiting.

apps/api/scripts/smoke-health.ts is the plan's end-to-end gate: import createApp, listen on port 0, read the assigned port from server.address(), fetch http://127.0.0.1:<port>/v1/health, require status 200 and body.db === "ok", print the body, then close the server, call disconnectPrisma(), and exit 0; on any mismatch or fetch failure print the observed status/body and exit 1. The script must not swallow errors — its exit code is the only signal the verify block has.
