    - floors: same round-trip, with buildingId required and level unique per building
    - classrooms: same round-trip, with floorId required and roomNumber unique per floor
    - departments: same round-trip, with name and code unique
    - faculty: same round-trip, with email unique and departmentId required
    - authorisation: no token → 401 on every write; user token → 403 on every write; user token → 200 on every read
    - referential guards: DELETE building with floors → 409; DELETE floor with classrooms → 409; DELETE department with faculty → 409
    - validation: a missing required field or a non-positive metersPerPixel → 400 with code VALIDATION_ERROR
    - duplicates: a second POST with the same natural key → 409 with code CONFLICT
    - serialisation: floor.metersPerPixel is a string in JSON, never a nested object
  </behavior>

Create packages/shared/src/schemas/catalog.ts with zod create and update schemas for all five entities and append `export * from "./schemas/catalog.ts"` to the barrel. Fields: building { code 2-16 chars uppercase-ish, name, campus? }; floor { buildingId, level integer 0-20, name?, imagePath?, imageSha256?, widthPx?, heightPx?, metersPerPixel coerced number, positive, max 10 }; classroom { roomNumber, name?, floorId, departmentId?, entranceNodeId?, capacity? integer positive }; department { name, code }; faculty { name, email, designation?, departmentId }. Update schemas are the create schemas with every field optional, but must never allow an empty body — refine each to require at least one key.

Create modules/catalog/service.ts: thin Prisma functions per entity (list, getById, create, update, delete) plus DTO mappers that convert Prisma Decimal columns to strings (metersPerPixel, x, y, costM) and attach the relation summaries the admin screens need (floor includes building { id, code, name }; classroom includes floor and department summaries; faculty includes department summary). Map Prisma error codes to API errors: P2025 to 404 NOT_FOUND, P2002 to 409 CONFLICT naming the natural key, P2003 to 409 CONFLICT with a message naming the blocking child rows. Before deleting a building, floor or department, count dependents (floors, classrooms plus nodes, faculty plus classrooms) and return 409 with a message stating what must be removed first, rather than relying on a raw foreign-key error.

Create modules/catalog/router.ts mounting, per entity, GET /, GET /:id, POST /, PATCH /:id and DELETE /:id under /v1/buildings, /v1/floors, /v1/classrooms, /v1/departments and /v1/faculty. Reads require requireAuth only (the mobile client must be able to read classrooms for search); writes stack requireAuth then requireRole("admin"). Support filters that the admin screens and later search will use: floors by buildingId, classrooms by floorId or buildingId, faculty by departmentId, classrooms by departmentId. Parse every body with the shared zod schema, returning 400 VALIDATION_ERROR with issue paths on failure. Export the router; mount it in app.ts between the admin router and the 404 handler.

Build the parent/child cases in dependency order (building then floor then classroom; department then faculty) inside their own describe blocks so the 409 guards are tested with real children present.

Invariants, all queried from the database and ignoring fixture rows whose building code starts with FIX-:

2. every floor has metersPerPixel greater than 0 and no floor uses 1.0;

5. no node has zero incident edges;
6. all five catalog entity types have a non-zero row count;
7. an admin user exists;
8. every edge has costM greater than 0;
9. at least one room number appears in two or more buildings;
10. each demo building's node/edge graph is a single connected component (union-find over walk and vertical edges).
Violations must name the offending id or code so the message is actionable.
